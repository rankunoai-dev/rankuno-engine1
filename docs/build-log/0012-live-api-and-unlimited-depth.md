## 2. Corrections to earlier claims

**This section first, because a wrong number that was published and quietly
fixed is worse than one never published.**

### 2.1 The WordPress doctype fix does not explain gep.com's missing URLs

The plan for this cycle stated that WordPress SEO plugins wrap sitemaps in an
HTML doctype, that the parser was discarding those files, and that fixing it
would restore "~3,000+ missing sitemap URLs" on gep.com.

The first two claims are true in general. **The third is false for gep.com**, and
I verified it directly rather than assuming:

```
https://www.gep.com/sitemap.xml -> 200 len=992101
   head: <?xml version="1.0" encoding="UTF-8"?> <!--Generated by the Simple XML Sitemap Drupal module...
   PARSED kind= URLSET locations= 4427
```

gep.com runs **Drupal's Simple XML Sitemap module, not Yoast or RankMath**. The
file carries no doctype at all. It parsed to 4,427 URLs before this change and
parses to 4,427 URLs after it. The doctype rejection was never involved.

The actual cause of the low sitemap count in the first live run was the **page
budget**, not the parser. With `max_pages=200` and the 20% DOM reserve (ADR
0007), only 160 slots were available before the crawl, so 160 of 4,427 sitemap
URLs entered the graph. Re-run with room:

```
max_pages=6000, crawl_dom=False
STATUS succeeded in 10.0 s
total_urls 4427 | from_sitemap 4427 | sitemaps_fetched 1 | truncated False
```

The parser change is still worth having — it is correct, it is tested, and it
will matter on the many client sites that do run Yoast. But it was sold on a
premise that did not hold for the site used to justify it, and no measurement in
this cycle demonstrates it recovering a single real URL on a real site. Treat
"restores 3,000 URLs" as **withdrawn**.

### 2.2 "The sandbox is blocking network access"

Mid-cycle I stated that a failing command proved the environment blocked
outbound network access. That was wrong — `pip download fastapi` succeeded
moments later from the same shell. The exit-34 failures were specific to
`pip install -e` and to one crawl invocation, and remain undiagnosed. I should
not have generalised from one failure to a claim about the environment.

## 3. Why this cycle

The UI and the engine agreed on *shape* — `schema.ts` is generated from the
Pydantic models and the Python gate fails if it goes stale — but there was no
runtime connection. The data path was:

```
run a script by hand -> export_ui_fixtures.py -> src/data/*.json -> Vite bundles it -> MockAdapter
```

Crawling a new site meant re-running the exporter and reloading the page. The
`CrawlDataAdapter` seam and the `JobStatus` lifecycle had been built in cycle
0011 precisely so this cycle would be an addition rather than a rewrite, and
that held: `App.tsx` chooses the adapter, and no component changed.

## 4. What landed

### `src/core/state_store.py` — durable job records

Domain-agnostic by necessity and by design. `core/` may not import from
`modules/` (CLAUDE.md §1), so typing `JobRecord.result` as
`PageClassificationOutput` — as the plan specified — would have been a build
failure. A job carries an opaque `request` mapping in and an opaque `result`
mapping out; the API layer validates at its own boundary. The same store will
hold PPC and research jobs unmodified.

* One JSON file per job, plus a **separate** result blob. A finished 20k-page
  result is ~16 MB; listing jobs must not read it.
* Writes go to a temp file in the destination directory, then `os.replace`.
  Atomic, so a killed process leaves the old record or the new one — never a
  half-written one that fails to parse and takes the job with it.
* `finish()` writes the blob **before** the metadata. A reader learns a result
  exists only from `has_result`, so a crash between the two writes leaves a job
  that looks unfinished rather than one advertising a result that is not there.
* `recover_orphans()` fails every non-terminal job at startup.
* Ids are generated, never accepted from a caller — every id becomes a filename,
  so a client-supplied id is a path-traversal parameter.

### `src/api/` — a fourth layer

`api -> modules -> integrations -> core`. Recorded as ADR 0008.

Endpoints: `POST /api/v1/jobs` (202), `GET /jobs`, `GET /jobs/{id}`,
`GET /jobs/{id}/result`, `GET /health`.

The layer implements **no safety control of its own**. Everything is inherited
from `BaseTool.run()`. The one apparent exception, the URL check on `POST /jobs`,
is the same `UrlSafetyPolicy` the crawl would use anyway, run at admission so a
rejection is a `400` an operator sees. Verified against the running server:

```
SSRF localhost -> 400 {'detail': "Refused to fetch 'http://127.0.0.1:8000/': port 8000 is not permitted (allowed: 80, 443, 8080, 8443)"}
SSRF metadata  -> 400 {'detail': "Refused to fetch 'http://169.254.169.254/': host resolves to 169.254.169.254 — link-local address (cloud instance metadata range)"}
```

### Unlimited link depth

`max_depth` becomes `int | None`, defaulting to `None`. This is bounded, not
unbounded: `graph.record_links` drops targets the graph refused, and the graph
refuses new nodes at `max_pages`, so the frontier drains. `max_pages` was always
the real limit — a depth ceiling never reduced how many pages were fetched, it
only decided *which* pages filled the budget, and a default of 5 silently
truncated deep sites that still had budget left.

### Sitemap root-element slicing

The parser now slices out `<urlset>`/`<sitemapindex>` and parses only that. This
is **stricter** than the rule it replaced, not looser: XML permits a DTD only in
the prolog, so a slice starting at the root element cannot contain an entity
declaration. Any surviving `&ref;` is an *undefined* entity, which expat rejects.
Billion-laughs and XXE stay closed, and legitimate wrapped sitemaps stop being
thrown away. See §2.1 for what this does **not** demonstrate.

### Frontend

`httpAdapter.ts` with backoff polling (500ms → 5s, then flat), a live-crawl modal,
and adapter selection in `App.tsx`. The offline fallback is **announced**: fixture
data looks identical to crawl output on screen, so silently handing someone
`example.com` data would be the "confidently misread the screen" failure this
codebase keeps guarding against.

`startJob` is **optional** on `CrawlDataAdapter`. `MockAdapter` reads
pre-generated files and genuinely cannot start a crawl; its absence hides the
button rather than offering an action that throws.

## 5. Bugs found and fixed

### 5.1 Every API request returned 422 (bug in this cycle's code)

`from __future__ import annotations` makes every annotation a string, and FastAPI
resolves those against the **module** namespace. The dependency alias
`StateDep = Annotated[ApiState, Depends(get_state)]` was defined *inside*
`create_app()`, so FastAPI could not resolve it, fell back to treating the
parameter as a query parameter, and returned 422 for every request including
`GET /health`. Fixed by closing over the state directly — a closure has no such
failure mode.

### 5.2 A self-closing `<urlset/>` swallowed the wrapper (bug in this cycle's code)

Caught by a test written before the code was believed finished. With no closing
tag the slice fell through to "return everything from the root onward", which for
a wrapped sitemap included the trailing `</body></html>`, and the parse failed. An
empty sitemap is valid, not broken. Fixed with a quote-aware scan for the end of
the opening tag.

### 5.3 `JobStore.list` shadowed the builtin

`def list(self) -> list[JobRecord]` — inside the class body, `list` resolves to
the method, so mypy rejected the annotation. Renamed to `list_jobs()` rather than
worked around; the shadowing was a genuine footgun.

### 5.4 The exporter could not render `Annotated`

Making `max_depth` an `Annotated[int, Field(ge=0, le=15)] | None` broke
`export_ui_contract.py`, which raised `UnmappedTypeError`. That is the guard
working: it refuses to emit `any` rather than silently degrading the contract.
Taught it to unwrap `__metadata__`, and pinned the behaviour with a test.

## 6. Deliberate deviations from the plan

| Plan said | Built instead | Why |
| :--- | :--- | :--- |
| `JobRecord.result: PageClassificationOutput` | Opaque `Mapping[str, object]` | `core -> modules` is a build failure (CLAUDE.md §1) |
| `BackgroundTasks` worker | `asyncio.to_thread` | `execute()` is sync and calls `asyncio.run()`; on the event loop it would block the polling endpoint for the whole crawl |
| `fastapi`/`uvicorn` in core `dependencies` | `api` extra, installed by `bootstrap.ps1` | A library consumer should not get a web server; the bootstrap change keeps the gate green on a fresh clone |
| `progress: float` 0.0–1.0 | `queued`/`running`/terminal only | No progress hook exists; a fraction would be invented. Operator chose the honest option |
| `scratch/crawl_gep_full_20k.py` | `scripts/run_crawl.py --depth` | Scratch files must be deleted before the gate anyway |
| Modify `url_rules.py` for depth | No change | `max_depth` does not appear in that file |

## 7. Explicitly not done

* **No authentication on the API.** Acceptable only because `serve()` binds
  `127.0.0.1`. Blocking before any hosted deployment.
* **No real progress reporting.** The header shows an indeterminate indicator.
* **No job cancellation.** A started crawl runs to completion; there is no
  `DELETE /jobs/{id}`.
* **No crawl checkpointing.** Orphan recovery marks interrupted jobs `FAILED`
  because the work genuinely is lost. `state_store.py` now exists but does not
  yet checkpoint *within* a crawl, so CLAUDE.md §8's entry about interrupted
  crawls losing their work still stands.
* **Single process only.** The concurrency counter and the store lock are
  in-process.
* **No frontend tests.** `rankuno-ui` has no test runner. The 877 tests are all
  Python; `httpAdapter.ts` is covered by nothing but `tsc` and manual use.
* **No `rankuno-ui/README.md`** yet.
* **The 20k-page target is unverified end-to-end.** The largest live run this
  cycle was 4,427 URLs sitemap-only and 200 URLs with DOM crawling.

## 8. Live verification

Full stack, real network, through the running server:

```
ACCEPTED 202 {'id': 'b51e6f60...', 'status': 'queued', 'label': 'https://www.gep.com/'}
FINAL STATUS partial | error: None | elapsed 24.1 s
total_urls 200 | sitemap 160 | dom 41 | cms 0
pages_fetched 41 | sitemaps_fetched 1 | truncated True
classified 200 | unknown 186 | orphans 159
```

**186 of 200 pages classified `UNKNOWN` is not a success.** It is the expected
consequence of the budget: 160 URLs came from the sitemap with no HTML fetched
for them, and a URL with no body has almost no signals to classify on. Phase 1's
stated goal is zero unknowns, so this number is a defect signal about running the
engine at a page ceiling far below the site's size — not evidence the classifier
works. A meaningful accuracy measurement needs a budget that lets the DOM crawl
actually fetch the pages it discovered.
